## Overview

This command transforms **visual specifications** into **technical design specifications**. This is Layer 3 of the four-layer spec system:

1. **Requirements Spec** (spec.md) - Simple user stories
2. **Visual Spec** (visual-spec/) - UI designs, flows, contracts ← **INPUT**
3. **Design Spec** (design-spec.yaml) - Technical design ← **THIS COMMAND**
4. **Implementation Spec** (implementation-spec.yaml) - From code

The design spec is **machine-readable** and used by AI during implementation. It is generated from the **human-reviewed** visual spec.

## Purpose

The design spec layer:
- Translates visual/UX specifications into technical requirements
- Defines exact data models, API implementations, and component structures
- Serves as the "contract" that implementation will be verified against
- Is generated by AI, so it saves manual work
- But is derived from human-reviewed visual spec, so it's trustworthy

## Execution Steps

### Step 1: Setup and Prerequisites

```bash
# Run prerequisite check
.specify/scripts/bash/check-prerequisites.sh --json --paths-only
```

Parse JSON output for:
- `FEATURE_DIR`: The feature directory path
- `FEATURE_SPEC`: Path to spec.md

**Check prerequisites**:
- `FEATURE_DIR/spec.md` must exist (requirements spec)
- `FEATURE_DIR/visual-spec/` must exist (visual spec)
- If visual spec is missing: ERROR "Run /speckit.visualize first"

**Load context**:
1. Read `FEATURE_DIR/spec.md` (requirements)
2. Read `FEATURE_DIR/visual-spec/README.md` (visual spec index)
3. Read all files in `visual-spec/pages/` (UI specifications)
4. Read all files in `visual-spec/contracts/` (API contracts)
5. Read `.specify/memory/constitution.md` (project principles)

### Step 2: Extract Technical Requirements from Visual Spec

From visual-spec/**pages/**, extract:
- **UI Components**: All interactive elements (inputs, buttons, forms, etc.)
- **Validation Rules**: All client-side and server-side validations
- **State Management**: All UI states mentioned (loading, error, success, etc.)
- **Data Flow**: How data moves between components and APIs

From visual-spec/**contracts/**, extract:
- **API Endpoints**: All defined endpoints
- **Request/Response Schemas**: Exact data structures
- **Error Handling**: All error responses
- **Data Models**: Inferred from API contracts (user, session, etc.)

From visual-spec/**flows/**, extract:
- **Business Logic**: Sequences of operations
- **Integration Points**: Where different parts connect

### Step 3: Load Design Spec Template

Read the design spec template:

```bash
cat .specify/templates/design-spec-template.yaml
```

This template defines the **exact structure** that design-spec.yaml must follow.

### Step 4: Generate design-spec.yaml from Template

Using the template as your guide, create `FEATURE_DIR/design-spec.yaml` by:

1. **Load the template**: Read `.specify/templates/design-spec-template.yaml`
2. **Fill in metadata**:
   - `version`: Use "1.0.0"
   - `feature.id`: From spec.md
   - `feature.name`: From spec.md
   - `feature.branch`: From spec.md
   - `generated_at`: Current timestamp

3. **Fill in technical_context**:
   - `language`: From constitution.md or infer from project
   - `framework.backend`: From constitution.md or infer
   - `framework.frontend`: From constitution.md or infer
   - `database.type`: From constitution.md or infer
   - `testing.backend.framework`: From constitution.md (e.g., "jest", "pytest", "go-test")
   - `testing.frontend.framework`: From constitution.md (e.g., "jest", "vitest")
   - `testing.coverage_requirement`: Use 80
   - `project_structure`: From constitution.md or use default

4. **Fill in data_models**: Extract from visual-spec/contracts/*.yaml
   - For each API contract, identify the data models involved
   - Map all fields with exact names from contracts
   - Define database tables and indexes
   - **IMPORTANT**: Use exact field names from contracts (no camelCase conversion)

5. **Fill in api_endpoints**: Directly from visual-spec/contracts/*.yaml
   - Copy all endpoint definitions
   - Include exact request/response schemas
   - Include all validation rules and error messages
   - Add `source` reference to visual-spec file

6. **Fill in ui_components**: Extract from visual-spec/pages/*.md
   - For each page, identify components
   - Define props, state, and behavior
   - Link to API endpoints used
   - Add `source` reference to visual-spec file

7. **Fill in business_logic**: Extract from visual-spec/flows/*.md
   - Define each workflow
   - Break down into steps
   - Identify dependencies
   - Add `source` reference to visual-spec file

8. **Fill in file_structure**:
   - Define expected file paths for models, services, controllers
   - Define expected file paths for UI components
   - Follow project structure conventions

9. **Fill in traceability**:
   - Link back to user stories in spec.md
   - Link to visual-spec pages, contracts, flows

**Key Principles**:
- **Follow the template structure exactly** - do not add or remove sections
- Every section must reference its `source` in visual-spec/
- Field names must be **EXACT** from contracts (no interpretation)
- All data comes from visual spec (no hallucination)
- If something is unclear, mark it with "TODO: [clarification needed]"
- Replace ALL placeholder values in the template

### Step 5: Validate Design Spec Against Visual Spec

**Critical validation**:
1. **Field name consistency**: Every field in design-spec must match visual-spec contracts exactly
2. **Completeness**: Every API in visual-spec/contracts must be in design-spec
3. **Every UI component must have API dependencies listed
4. **Traceability**: Every design-spec section must have a `source` reference

Generate validation report:
```
Design Spec Validation:
✅ All API contracts from visual-spec are included
✅ All field names match exactly
✅ All UI components have API dependencies
✅ All sources are referenced
⚠️ Assumption made: [if any]
```

### Step 6: User Review (Optional but Recommended)

**Present to user**:
1. Show generated design-spec.yaml (or summary)
2. Highlight any assumptions made
3. Ask: "Does this technical design match the visual spec?"

**Handle feedback**:
- If user requests changes: Update design-spec.yaml
- If user approves: Proceed to finalization

### Step 7: Finalization

1. Save design-spec.yaml
2. Generate summary report
3. Update feature status

### Step 8: Report

Output:
- Path to design-spec.yaml
- Summary of what was generated (X models, Y endpoints, Z components)
- Validation results
- **Next command**: `/speckit.breakdown` (to generate work packages from design spec)

## Error Handling

- If spec.md is missing: ERROR "Run /speckit.specify first"
- If visual-spec/ is missing: ERROR "Run /speckit.visualize first"
- If visual-spec/contracts/ is empty: ERROR "No API contracts found in visual spec"
- If constitution.md is missing: WARN "No constitution found, using defaults"
